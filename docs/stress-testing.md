# Disposable-host stress testing

[English](stress-testing.md) · [繁體中文](stress-testing.zh-Hant.md)

`tools/loadtest` generates bounded, synthetic traffic against explicitly owned
test hosts. It is a development tool, not another release executable. Build it
with the project's mise environment:

```sh
mise exec -- go build -trimpath -o bin/loadtest ./tools/loadtest
```

For another architecture, set `GOOS` and `GOARCH` when building. Run the origin on
an isolated test peer. It serves generated bytes, with no filesystem access and
an 8 MiB response limit:

```sh
./bin/loadtest --owned-target --listen 192.0.2.30:18082
```

On a separate load generator, explicitly select the route:

```sh
./bin/loadtest --owned-target \
  --target 'http://192.0.2.30:18082/bytes?bytes=8388608' \
  --protocol connect --proxy 192.0.2.20:17890 \
  --workers 32 --duration 15s --timeout 15s

# New connections, not 128 simulated physical devices:
./bin/loadtest --owned-target \
  --target 'http://192.0.2.30:18082/bytes?bytes=65536' \
  --protocol connect --proxy 192.0.2.20:17890 \
  --workers 128 --fresh --duration 15s --timeout 15s
```

The addresses above are documentation examples. Replace them with owned test
addresses, allow only the load generator in Rillway's source ACL, and restrict
the origin port to test machines. Never point this load at third-party websites,
VPN endpoints, company services, or production hosts. The ownership flag is an
explicit operator acknowledgment; it does not prove ownership or enforce a
private-address boundary.

| Option | Meaning |
| --- | --- |
| `--owned-target` | Required acknowledgment for both server and generator |
| `--listen HOST:PORT` | Origin mode; foreground until stopped |
| `--target URL` | HTTP origin; user-info credentials and redirects rejected |
| `--protocol` | `direct`, HTTP forwarding `http`, TCP tunnel `connect`, `socks5` |
| `--proxy HOST:PORT` | HTTP/CONNECT or SOCKS listener, without proxy authentication |
| `--workers` | 1–1024 concurrent workers |
| `--duration` | 1 second–5 minutes, default 15 seconds |
| `--timeout` | Per-request and tunnel setup limit, 100 ms–1 minute; default 15 seconds |
| `--fresh` | New TCP connection for every request instead of client reuse |

Environment proxies are ignored. CONNECT carries test HTTP bytes inside a TCP
tunnel; this benchmark does not include destination TLS encryption, HTTPS
interception, SOCKS UDP, upload throughput, or browser rendering. To test a VPN,
use an owned peer reachable through that provider and a fixed Rillway rule. The
WireGuard/Tailscale peer must expose the same bounded response endpoint; no host
DNS fallback or VPN state cloning is required.

Output contains counts, bytes, Mbit/s, request rate, and response-duration p50/p95
in 1 ms buckets. Latency includes the full body, not just connection establishment.
Buckets end at 60 seconds; `latency_capped` marks overflow. Partial response bytes
count toward throughput, while only complete HTTP 200 responses with the
declared length count as completed. Work interrupted at the overall deadline is
reported separately from failures. Zero completions or request failures produce
a nonzero exit status. No destinations, request bodies, headers, credentials, or
upstream error strings are printed or retained by the generator.

## Resource profiles and interpretation

As one real hardware reference, the [GL.iNet Beryl AX specifications](https://www.gl-inet.com/products/gl-mt3000)
list a dual-core 1.3 GHz processor, 512 MB RAM, and a Gigabit LAN port. A VM with
matching memory/core counts does not match that processor's performance.

[OrbStack](https://docs.orbstack.dev/machines) supports per-machine CPU and memory
limits. In this environment CPU quotas still exposed 18 CPU indexes. Apply a
temporary Rillway-only [systemd CPUAffinity](https://github.com/systemd/systemd/blob/main/man/systemd.exec.xml)
drop-in to restrict the daemon to one or two indexes, restart it, and verify
`Cpus_allowed_list` for its actual PID. Also inspect the effective machine
`cpu.max`, `memory.max`, and `memory.swap.max`. Do not modify global OrbStack
configuration or unrelated machines.

Use a dedicated origin/load generator outside the constrained machine. Reset
the daemon before each profile to avoid carrying retained heaps across limits.
Keep the official WARP daemon enabled when evaluating the complete installation;
its memory is outside Rillway's RSS. Keep Docker outside the tested budget unless
Docker resource consumption is deliberately part of the workload.

For a Gigabit scenario, only the disposable machine's interface receives a
temporary TBF egress shaper: `rate 1gbit burst 256kb latency 50ms`. Inspect its
counters and remove it after testing. This is an aggregate egress ceiling, not
an exact simulation of a full-duplex NIC, Wi-Fi, or a WAN. OrbStack's shared kernel
and fast Mac CPU can offload work beyond a daemon's CPU affinity; VM speeds cannot
be advertised as router speeds.

Sample process RSS, service and machine cgroup memory, anonymous memory, swap,
CPU counters, file descriptors, PID stability, OOM counters, and authenticated
`/api/v1/stats` latency once per second. Use the generated TLS certificate and
read the token from a private file. Never put the token in arguments, logs, or
public artifacts. Check the actual outbound and active-connection count in the
snapshot. Flow retention reaching 2048 is an observation limit, not a supported
connection limit.

## Measurements: 2026-10-05

A pre-release development binary was tested on disposable Ubuntu
26.04 arm64, using a separate Ubuntu 24.04 origin/generator. WARP remained idle,
Docker was paused, swap was disabled, and aggregate egress was shaped to 1 Gbit/s.
Each individual workload ran for 15 seconds with a 15-second request timeout.

| Machine budget | Observed result |
| --- | --- |
| 256 MiB / 1 CPU | HTTP, CONNECT, SOCKS5 and 128-worker connection churn completed with valid monitoring. Tailscale monitoring exceeded the timeout; the profile was aborted and WireGuard was not run. Full VPN stability remains unverified |
| 512 MiB / 1 CPU | All six workloads completed with valid monitoring and zero request/API failures or OOM kills. WireGuard reached 555.8 Mbit/s and Tailscale 597.4 Mbit/s. Machine memory reached the 512 MiB ceiling; Rillway RSS peaked at 308.0 MiB |
| 512 MiB / 2 CPUs | Five workloads had valid monitoring. WireGuard downloaded data, but complete monitoring timed out again on rerun; it remains unverified |
| 1 GiB / 2 CPUs | All six workloads completed with valid monitoring and zero request/API failures or OOM kills. HTTP/direct: 624.2 Mbit/s; CONNECT/direct: 582.9; SOCKS5/direct: 577.1; Tailscale: 677.0; WireGuard: 450.7. Machine memory peaked at 621.2 MiB during WireGuard |

A 60-second mixed test at 1 GiB / 2 CPUs ran 32 direct, eight WireGuard and eight
Tailscale connections, each requesting 1 MiB. All three outbounds and 48 active
connections were confirmed by the management API. Aggregate throughput was
674.7 Mbit/s, with 4,805 complete downloads, zero request/API failures, a stable
PID, and zero OOM kills. The deadline cancelled 48 unfinished requests separately.
Rillway RSS peaked at 322.9 MiB, machine memory at 576.3 MiB, and maximum
management API response time at 22.5 ms.

These measurements support a **1 GiB / 2 CPU starting budget** for an Ubuntu VM
running this provider combination. They do not establish a stable 256/512 MiB
minimum, physical-router throughput, or CPU scaling: each basic workload was
measured once, and the mixed run lasted only one minute. IPv6, upload throughput,
destination TLS, WARP/WARP+ public download stress, router flash capacity,
OpenWrt installation, and hours/days of soak testing were not measured. Initial
five-second-timeout failures and incomplete monitoring records were preserved,
not reclassified as successful. Machine budgets, shaping and service overrides
were restored, and paused Docker services resumed after testing.

Keep raw measurements and operator addresses under ignored `.local/` directories
with `0700` directories and `0600` files. A missing monitor, changed effective
limits, a restarted PID, no completed downloads, or an incomplete workload must
remain a failed/unverified result. Restore machine allocations, temporary unit
drop-ins, shaping, and paused services after the test. See [dated measurements](verification.md).
